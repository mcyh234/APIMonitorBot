# 新闻监听日志与排障

升级并重启后开始记录，历史故障不会自动生成日志。诊断不会关闭审核或重发基线之前的帖子。

管理员聊天命令（受 `/newswatch` 或 `/tibowatch` 命令开关控制）：

```text
/newswatch logs
/newswatch logs @thsottiaux
/newswatch retry
```

`logs` 返回最近 15 条日志与队列概况，指定账号可筛选；拦截记录仅保留全局固定原因与计数。`retry` 将待发送项的重试时间提前到下一轮，不直接发送、不清零失败次数、不清除游标或去重记录。来源限流仍遵守原来的退避时间。监听关闭时需先开启，模型失效时需先修复配置。

WebUI「监控管理 → AI 消息监听 → 新闻监听日志与排障」提供最近 300 条记录、账号筛选、阶段耗时、待发送对象和重试时间、手动刷新及 JSON 导出。展开时每 10 秒刷新，界面最多展开 60 条匹配记录；导出包含完整的最近 300 条记录。API `GET /api/tibo-watch/logs` 和 `POST /api/tibo-watch/retry` 均要求 WebUI 登录。

| 最近阶段或现象 | 含义与处理 |
| --- | --- |
| 没有轮次启动 / 长期停在旧阶段 | 检查部署是否重启、进程与调度器是否仍在运行；重启前的阶段记录可能保留 |
| 来源抓取失败或超时 | 展开「各账号抓取状态」检查各域名的限流、503 或冷却时间；一个来源失败不表示全部来源失败 |
| 首次建立基线 | 只记录当前 ID，不补发首次启动之前的历史 |
| 来源抓取完成但发现 0 条 | 该轮来源中没有未处理且高于安全基线的可入队帖子；已处理 ID、初始历史和本地规则拦截不会入队 |
| 检查审核模型配置 | 审核未配置、已停用或选择的配置被删除时暂停；用 `/reviewmodel status`、`list` 检查 |
| 读取帖子详情与翻译 | 包含回复背景、评论和翻译；总等待最多 120 秒，可用 `/translatemodel status` 检查所选模型 |
| 审核原文、译文与上下文 | 最多等待 60 秒，审核不确定或不可用不会发送 |
| 内容审核明确拦截 | 整帖跳过；只保存固定分类与计数，不留正文与模型自由文本 |
| 等待通知发送确认 | 最多等待 30 秒；失败继续保留加密任务，检查 OneBot 连接、群权限等 |
| 通知已确认送达 | 收到成功确认并持久化 ACK 后记录；不会将生成图片当成成功推送 |
| 退避等待，后帖积压 | 自动重试从 60 秒逐步延长到 1 小时；同一账号、同一对象保序，前帖失败会延后后帖，可修复故障后执行 `retry` |

每轮仍最多抓取 12 个账号、发送 3 条帖子。整轮最多 600 秒；超时取消剩余工作，已保存的加密队列在下一轮继续。被取消的阶段不视为成功送达。网络发送后但确认前断开，仍可能无法判断对端是否收到，日志不宣称跨系统恰好一次。

日志只记录固定阶段、账号、帖子 ID、通知对象、时间、耗时与计数，不记录正文、译文、模型回复、异常原文或带凭据的 URL。内容审核拦截事件进一步只保留时间、固定分类与计数。新闻素材仍保存在原有加密队列中，与诊断记录分开。

来源冷却现可显示「本账号的该来源」或「整个来源域名」，以及原始 HTTP 状态和固定原因。普通抓取错误最长退避 300 秒；这是 RSS 抓取策略，与待发送队列的最长 1 小时重试不同。明确的上游 `Retry-After` 可能更长，仍须等待；`/newswatch retry` 只提前处理待发送项，不解除来源冷却。

RSS 只读诊断（不调用模型、不发送通知、不读数据库、不使用 X Token）：

```powershell
.\.venv\Scripts\python.exe scripts/check_news_sources.py --username thsottiaux --post-id 帖子ID
```

2026-10-21 的一次只读检查中，FxTwitter、`nitter.jaydenha.uk`、`nitter.netbub.com` 返回正常且最新 ID 一致；`nitter.kareem.one` 返回 503。可用性会变化，这次结果无法证明某次实际漏报发生在哪个阶段，应结合部署上的日志和具体帖子 ID 排查。
